## 2. First divergent CABAC bin / element / context, and coder state

```
x264 golden bins: 34391; Phoenix bins: 40861
FIRST DIVERGENT BIN: index 5 (0-based, bin #6)
  bin 1     x264: ctx=399 b=0 dec    phx: ctx=399 b=0 dec
  bin 2     x264: ctx=68  b=1 dec    phx: ctx=68  b=1 dec
  bin 3     x264: ctx=68  b=0 dec    phx: ctx=68  b=0 dec
  bin 4     x264: ctx=69  b=1 dec    phx: ctx=69  b=1 dec
  bin 5     x264: ctx=69  b=1 dec    phx: ctx=69  b=0 dec   <== FIRST DIVERGENCE
  x264 element: intra4x4_pred_mode (:83-96)
  phx  element: intra4x4_pred_mode (:83-96)
  x264 record: dec ctx=69 b=1 state=121 low/range 6560/436 -> 6560/258   intra4x4_pred_mode (:83-96)
  phx  record: dec ctx=69 b=0 state=121 low/range 6560/436 -> 13636/356  intra4x4_pred_mode (:83-96)
  coder state before bin: MATCH (x264 low/range 6560/436, phx 6560/436)
REMAINING DIVERGENCE: 0 inserted/deleted bins removed; tail agrees for 5 bins;
  next mismatch at aligned index 5: x264=('dec',69,1) phx=('dec',69,0)
```

Interpretation:

* The first five ordered bins of the slice match exactly: `mb_type` (ctx 3,
  `I_4x4`), `transform_size_8x8_flag` (ctx 399, 0), and the first two
  `intra4x4_pred_mode` groups (ctx 68/68). The sixth bin is the first rem-mode
  bit of the second 4x4 block.
* The **arithmetic coder state matches exactly** at the divergent bin: same
  context index (69), same context state (121), same `i_low/i_range`
  (6560/436) before encoding. Therefore the divergence is **not** in CABAC
  state propagation, renormalisation, or context init; it is a different
  **bin value fed to an identical writer** — i.e. `i_pred`/`i_mode` reaching
  `cabac_intra4x4_pred_mode` differ.
* The divergent writer is byte-identical in the port: x264
  `encoder/cabac.c:83-96` vs `src/phx_cabac_syntax.c:216-229`; the predictor is
  x264 `common/macroblock.h:420-431` vs `src/phx_cabac_syntax.c:174-181`; the
  call site is x264 `encoder/cabac.c:417-428` vs
  `src/phx_cabac_syntax.c:563-573`. The differing values originate **upstream in
  I4 analysis/RD**, not in the entropy stage.
* With `subme=8 ⇒ mbrd=2`, that upstream stage is x264 `intra_rd()`
  (`encoder/analyse.c:982-1014`) and `intra_rd_refine()` (`:1016-1135`, I4 half
  at `:1086-1134`), whose `rd_cost_i4x4()` (`encoder/rdo.c:315-347`) encodes
  each candidate with a **copy of the live CABAC state** (`COPY_CABAC`,
  `rdo.c:71-73`) and full `x264_mb_encode_i4x4()` (`encoder/macroblock.h:132-166`).
  The Phoenix counterpart is `phx_analysis_intra_rd_refine_i4()`
  (`src/phx_analysis.c:885-933`) + `phx_analysis_rd_i4()` (`:848-878`), which is
  a luma-only reduced cost model with a local cache copy; this is the first
  place to look for the mode that produces the wrong rem bin.
* Total bin counts also differ (34391 vs 40861), and the tool reports **0
  inserted/deleted bins** around the first divergence: this is a value/choice
  divergence, not a stream-length artifact at that point.

Coefficient handoff (same tool):

```
COEFFICIENT HANDOFF (MB0 luma 4x4 arrays):
  blocks compared: 16; raw arrays equal: 6/16; equal after zigzag rescan: 0/16
  block 1: x264 [3,-1,-2,1,1,0] ... phx [7,-3,0,0,0,0] ... phx-zigzag [7,0,-3,0,0,0] ...
```

Caution on that last line: the tool's docstring claim (`tools/cabac_bin_diff.py:517-523`)
that "the Phoenix trellis handoff does not" zigzag-scan is **stale and
contradicted by the current source**. Phoenix scans before storing at
`src/phx_mbencode.c:316-317` (`scan[k] = dct[phx_zigzag4[k]]`, mirroring x264
`encoder/macroblock.c:873/889`) and again for chroma at `:764-777`; the check at
`tools/cabac_bin_diff.py:553-554` applies `ZIGZAG4` **a second time** to data
already in scan order, so `0/16 after zigzag rescan` is expected even when the
arrays are correct. Do not chase a phantom missing-scan bug; the real signal is
that coefficient arrays start diverging after the I4 mode decision diverges.

## 6. Explicit parity status

**`0/100 is not parity.** `build/parity/parity_report.json` totals:
`cases=100, compared=100, x264_ok=100, x264_failures=0, byte_exact=0,
mismatches=100`. The `slow` subset is `cases=10, byte_exact=0, mismatches=10`,
`first_diff_min=666` (earlier snapshot 39). Both `first_frame_probe.py` runs
exit 1 with `VERDICT: DIVERGENCE`; `cabac_bin_diff.py` exits 1 with a first
divergent bin at index 5. Exact SPS/PPS/SEI, an exact 30-bit IDR header, and
five matching CABAC bins are useful localisation evidence — they are **not**
byte-exact parity and must not be reported as progress toward "parity reached".
The only acceptable end state is 100/100 `byte_exact=true` for every preset,
fixture and entropy, including all 10 `slow` cases.
