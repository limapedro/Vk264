GOP=60 P-slice corruption finding (2026-11-20)
=============================================

The first benchmark run used --gop 60 (the harness's typical GOP setting) and
produced a stream that ffmpeg cannot decode cleanly:

  ffmpeg -v error -i vk264_ultrafast.h264 -f null -
  [h264] cbp too large (56) at 26 0
  [h264] error while decoding MB 26 0
  [h264] mb_type 790 in P slice too large at 30 0
  [h264] corrupted macroblock 15 0 (total_coeff=-1)
  [h264] negative number of zero coeffs at 25 0
  ... (many more)

x264's stream at the same settings decodes with zero errors.

Isolation test (30 frames, QP23):
  gop=1  -> 5,682,390 bytes, decode CLEAN
  gop=60 -> 1,599,062 bytes, decode ERRORS (first: cbp too large at 26 0)

Conclusion: the IDR/I-slice path is valid; the P-slice payload is corrupt on
real footage. This matches issue #50 (gop>1 P-slice payload diverges at offset
194 on synthetic patterns). The PSNR/SSIM from the gop=60 run are unreliable
because the decoded frames are corrupted. The clean benchmark therefore uses
gop=1 (all-IDR) so quality metrics are meaningful.

This is an active parity gap — not a benchmark artifact.
