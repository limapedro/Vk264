# Fresh all-preset audit — findings

Generated by `build/audit_presets.py` on 2026-11-23. 120 experiments:
2 clips (warzone2020, forza) × 3 lengths (2f, 8f, 30f) × 10 presets × 2
entropies, x264 vs oracle. MP4 pairs in this folder, raw H.264 in
`build/preset_audit_work/`, machine data in `manifest.json`, table in
`report.md`.

## Headline result

**12/120 streams byte-exact** — all 12 are `ultrafast` (2 clips × 3 lengths ×
2 entropies). Every other preset fails. The prior `tests/all_presets/`
sweep (24/320) is consistent.

## Visual artifacts (the green blocks you saw)

Decoding each MP4 to raw YUV and comparing with the source:

| preset family | entropy | oracle PSNR | green blocks | observation |
|---|---|---|---|---|
| ultrafast | both | 45.6 dB (2f) / 42.1 dB (30f) | 0 | byte-exact |
| superfast..slow | CAVLC | ~23–31 dB | 0 | visually plausible, not byte-exact |
| superfast..placebo | **CABAC** | **3.6–9.7 dB** | **126–1792 per clip** | **green / blank blocks** |
| placebo (forza) | CAVLC | 3.9–4.5 dB | 320–1600 | same artifact in CAVLC too |

Concrete example — `exp236_oracle_fulllen600_64x64_600f_slower_cabac.mp4`
(the file you quoted):

```
x264   frame0: Y[144,205]  avgU=123  avgV=134   (normal)
oracle frame0: Y[  0,212]  avgU=7    avgV=0     (broken from the first frame)
oracle frame1: Y[  0, 29]  avgU=0    avgV=0     (blank/green)
```

U=0 and V=0 are invalid chroma for this content — the decoder produces
uninitialized/green macroblocks. 596 decoded frames (600 requested), with
34154 green-ish and 31178 flat 8x8 blocks. This is not a compression artifact:
it is a malformed stream.

## Failure classes

1. **NAL0 byte5** (36 cases) — `slower`, `veryslow`, `placebo`: SPS mismatch.
   x264 emits `max_num_ref_frames=8` etc. for these presets; the oracle SPS is
   fixed. Note: the quoted mp4's ffprobe reports "8 Ref Frames", confirming
   the SPS is at least partially correct, but byte 5 still differs.
2. **NAL1 byte1 / byte3** (35 cases) — `superfast`..`slow`: PPS / first slice
   header mismatch.
3. **NAL COUNT** (36 cases) — `superfast`..`slow` at 30f and all 600f runs:
   x264 emits 12/34/36/40 NALs where the oracle emits 10/32/32/32 — x264 has
   scene-cut/slice-type I-frames the oracle's fixed `f % keyint` schedule
   never produces (this is the stage-03 slicetype/P7 work).
4. **2f non-ultrafast** — oracle output undecodable (0 frames decoded): a
   separate short-clip bug worth isolating.
5. **veryslow/placebo CAVLC at 8f/30f** — oracle decode returned no metrics;
   likely a hang/crash or empty output, needs a dedicated check.

## Root-cause evidence for the CABAC green blocks

`exp024` (superfast, CABAC, 8f) slice-header comparison:

```
x264   NAL0 (SPS) len=23 6764000aacd9442684000003000400000301e23c489658
oracle NAL0 (SPS) len=23 6764000aacd9442684000003000400000301e23c489658   IDENTICAL
x264   NAL1 (PPS) len=4  68ef89cb
oracle NAL1 (PPS) len=4  68ef89cb                                      IDENTICAL
x264   NAL2 (IDR) len=130 65888400ffec837a...
oracle NAL2 (IDR) len=204 65888400fffeca4f...
                                  ^^ byte 5 differs (0xec vs 0xfe)
```

SPS and PPS match exactly; the IDR slice header differs at byte 5 and the
slice payload lengths diverge sharply (130 vs 204 bytes). Since CABAC context
initialization depends on slice-header QP / cabac_init_idc, a mismatch there
desynchronizes the decoder — consistent with the invalid chroma observed.

`exp024` uses `--qp 28` on the x264 side and CLI args `25 28` (qp_i, qp_p) on
the oracle side.

Slice-header field dump (`build/sh_dump.py`, same `--qp 28 --cabac`):
```
ultrafast  IDR qp_delta=-3 cabac_init=0 idr=0 poc=0 fn=0 ; P qp_delta=0 poc=0
superfast  IDR qp_delta=-3 cabac_init=0 idr=0 poc=0 fn=0 ; P qp_delta=0 poc=2
slower     IDR qp_delta=-3 cabac_init=0 idr=0 poc=0 fn=0 ; P qp_delta=0 poc=2
```
`qp_delta`/`cabac_init` are identical across presets, so the green blocks are
NOT caused by a preset-specific QP/CABAC-init value. The differentiating
field is **POC** (0 for ultrafast, 2 for presets with B-frames) — i.e. the
stage-03 slice-type/POC machinery. A wrong POC in the oracle's slice header
desynchronizes CABAC decoding and yields invalid chroma. This ties the
visually broken streams directly to the stage-03 gap.

2f non-ultrafast cases (exp003/004/015/016, 063/064/075/076): the oracle
*does* emit a non-empty H.264 (297–408 bytes), but ffmpeg decodes **0 frames**
(`psnr=-1`). The streams are malformed for short clips too, independently of
the length-driven NAL-count issue.

## FIXED this session (header parity)

Two header bugs were found and fixed in `Vk264-rewrite/src/ref/nal.c`:

1. **PPS `chroma_qp_offset`** — x264's psy-RD (`encoder.c:1218-1231`) lowers
   it by 2 when `i_subpel_refine >= 6` (presets fast and above). The oracle
   always used 0. Fixed by setting `i_chroma_qp_offset = (i_subme>=6)?-2:0`
   at the end of `vk_param_apply_preset`. Verified: PPS bytes now identical
   for fast/medium/slow/veryslow/placebo.
2. **SPS `log2_max_frame_num_minus4`** — x264 (`set.c:161`) computes
   `max_frame_num = max_dec_frame_buffering * (b_pyramid?2:1) + 1`; the
   oracle omitted the ×2. Fixed. Verified: SPS bytes now identical for
   slower/veryslow/placebo.

Also fixed a harness bug: x264 "cavlc" cases lacked `--no-cabac` (x264
defaults to CABAC for non-ultrafast presets).

**Result:** after a fresh 120-case audit, NAL0/NAL1 mismatches are gone for
*every* preset. All remaining non-ultrafast failures now first diverge at
**NAL2 (the first slice)** — i.e. slice header/POC/slice-data, the stage-03
gap. The green blocks persist because POC still diverges.

## Bitrate / size is genuinely different (not just padding)

Aggregate NAL bytes across the audit show the oracle produces far fewer coded
bytes for most presets: e.g. 8f fast CABAC x264 5313 vs oracle 3819 (ratio
0.72); 2f fast CABAC x264 2724 vs oracle 1078 (ratio 0.40). This is not a
container artifact — the coded slice data itself is smaller/different because
the oracle lacks the analyser decisions (subpel ME, trellis, RD, adaptive
quant, B-frame决策). **Byte-exact parity requires these encoders to make
identical decisions**, so matching bitrate is a symptom of the same underlying
gap, not a separate cosmetic issue.

Full per-clip per-preset size/NAL tables: `PER_PRESET.md`, `manifest.json`.

## Slice-level analysis (NAL2) after header fixes

Bit-level comparison of the first IDR slice (`build/bit_diff.py`):

| preset | first differing byte | x264 prefix | oracle prefix |
|---|---|---|---|
| superfast | 5 | `65 88 84 00 ff ec 83 7a` | `65 88 84 00 ff fe ca 4f` |
| fast | 10 | `... ff fe ca 4f 81 4b 9c dc` | `... ff fe ca 4f 81 4b 9d 18` |
| slower | 10 | same as fast | same as fast divergence |
| veryslow | 11 | `... 81 4b 9c dc` | `... 81 4b 9d 18` |

Notable: the oracle's superfast IDR prefix (`ff fe ca 4f 81 4b`) matches
x264's *fast* prefix, while x264 superfast uses `ff ec 83 7a`. So the oracle
emits the same IDR slice header for all non-ultrafast presets, but x264 varies
one header field with the preset (likely `idr_pic_id`/POC-related).

**Decoder misalignment RESOLVED:** the missing field was `dec_ref_pic_marking()`
— x264 `encoder.c:330-334` writes `no_output_of_prior_pics_flag` and
`long_term_reference_flag` (2 bits) for IDR slices after POC. After adding
those, `build/slice_fields.py` decodes x264 and oracle identically:
```
superfast: first_mb=0 slice_type=7 pps_id=0 frame_num=0 idr_pic_id=0
           poc_lsb=0 no_output_prior=0 long_term_ref=0 qp_delta=-3
           disable_deblock=1  (28 header bits, BOTH)
```
**Conclusion: the entire IDR slice header is byte-identical.** The first
differing byte (5 for superfast, 10–11 for fast/slower/veryslow) lies in the
**macroblock payload**, not the header. All header/parameter-set parity is
complete; what remains is macroblock analysis + residual coding.

One concrete macroblock-level gap: `chroma_qp_index_offset` (now correctly
written to the PPS as −2 for fast+) is **not applied** by the oracle encoder —
`i4x4enc.c`/`cabac_enc.c` quantize chroma with the luma `qp`, while x264 uses
`qp + chroma_qp_offset` for chroma.

## ROOT CAUSE of the macroblock divergence (this session)

Instrumented x264's `macroblock_write_cabac_internal` (`build/mb_decisions_dump.py`)
and inspected the oracle's CABAC IDR encoder:

```
x264 exp024 (superfast, CABAC) first MBs:
XMB xy=0 type=0 (I_4x4) cbp=1  predmode=0
XMB xy=1 type=0 (I_4x4) cbp=47 predmode=0
XMB xy=2 type=2 (I_16x16) cbp=16 predmode=4
XMB xy=3 type=1 (I_16x16 chroma) cbp=17 predmode=4
```

The oracle's CABAC IDR path (`cabac_enc.c:497`) **always calls
`cabac_mb_type_i16`** — there is no I4x4 decision or encoder in that path
(`vk_encode_i4x4_mb` is only used by the CAVLC path). So the very first MB is
coded with the wrong type, which explains both the NAL2 payload divergence
and, via the resulting context desynchronization, the green blocks.

This is a substantial missing feature: full I4x4 support in the CABAC IDR path
needs the per-4x4 mode decision, 16 sub-block residual quantisation/CBP, and
the corresponding CABAC context coding (`cabac_mb_header_i` I4 branch). It is
the concrete blocker for superfast..placebo byte-exactness.

### Partial I4x4 experiment (reverted)

Attempted a first I4x4 integration: compute `vk_i4x4_decide()` cost, compare
to the I16 SATD, and if I4 wins emit `cabac_mb_type_i4` + 16 pred-mode
signals before the existing I16 residual path. Result **regressed badly**:
MP4 56/56 → 48/56, audit 12/120 → 6/120, and the first NAL2 diff moved
*earlier* (byte 10 → 5). Causes: (a) the raw-SATD comparison also selected I4
for ultrafast CABAC cases that must stay byte-exact, and (b) emitting an I4
mb_type with I16 residual/CBP coding produces a malformed MB. Reverted fully;
baseline restored (29/29, 56/56, 12/120).

### I16-vs-I4 decision uses rd_cost_mb, not SATD (definitive)

x264 `analyse.c:991` and `:1000` **overwrite** `a->i_satd_i16x16` and
`a->i_satd_i4x4` with `rd_cost_mb(h, a->i_lambda2)` — the actual quantized
residual RD cost (distortion + lambda2 × coded bits) after transform/quant.
The final MB-type comparison (`analyse.c:2943-2945`) uses those RD costs, not
the initial SATD. My oracle compares raw SATD/SAD, so its decision is not
comparable at all — this is why it picks I4 where x264 picks I16 despite a
"better" SATD. Correcting the decision requires an `rd_cost_mb` equivalent
for both I16 and I4 candidate modes (transform, quant, dequant, coeff bits),
i.e. effectively the atomic I4 path plus RD costing. This is the true scope of
the remaining parity work.

### I16-vs-I4 decision primitive is also wrong (this turn)

`build/test_i4_decision.c` measures the I16-vs-I4 decision on the ultrafast
audit clip (where x264 uses I16 for the first MBs):
```
I16 SATD=14358  I16 SAD=28674  I4(vk_i4x4_decide)=2040  -> both models pick I4
```
So even with x264's subme-dependent primitive (SAD for ≤1, SATD for >1), the
oracle's `vk_i4x4_decide` cost is far too low relative to I16 — it selects I4
where x264 selects I16. The decision itself must be corrected (cost units /
mode-bit penalties / neighbour reconstruction) **before** wiring an atomic I4
path; otherwise it will misfire exactly as the partial attempt did.

Conclusion: I4x4 support must be **atomic** — mb_type, 16 pred modes, CBP,
luma/chroma residual and reconstruction all together — before it can be
enabled. A partial implementation makes streams worse. This is the concrete
scope of the remaining work.

**FIXED:** added global `vk_chroma_qp_offset` (set by `vk_param_apply_preset`)
and applied `cqp = clip(qp + offset)` to chroma quantisation/dequantisation in
`i4x4enc.c`, `slice.c` and `cabac_enc.c`. Gates unchanged (ultrafast offset=0).
The 120-case audit verdict is unchanged (12/120) — chroma QP is not the driver
of the remaining macroblock divergence; the gap is in analysis/mode decisions.

## What this changes about the roadmap

- Stage 03 (slicetype) explains failure class 3 (NAL count) and is still
  blocked at 13/16 frame types.
- The CABAC green blocks are a **new, separate, high-severity bug** in the
  slice-header/CABAC-init path that affects *every* non-ultrafast CABAC
  encode — fixing it would turn visually broken streams into merely
  non-byte-exact ones, a large quality win independent of stage 03.
- SPS/PPS differences (class 1/2) are independent, localized header bugs.
