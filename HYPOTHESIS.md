# Oracle divergence hypotheses — video-level verification (2026-11-22)

## Evidence baseline

Numbered MP4 experiments in `tests/` (`exp001`…`exp008`), generated by
`build/make_video_experiments.py`. Metadata is recorded in
`tests/video_experiments.json` and is readable with ffprobe
(`codec_name=h264`, `profile=Constrained Baseline`, `64x64`, `yuv420p`,
`60/1`, `nb_frames=8`, `duration=0.133336`).

| experiment | encoder | clip / preset | result |
|---|---|---|---|
| exp001/002 | x264 / oracle | warzone, ultrafast, CAVLC | **BYTE-EXACT** |
| exp003/004 | x264 / oracle | forza, ultrafast, CAVLC | MISMATCH NAL 6 byte 102 |
| exp005/006 | x264 / oracle | forza, ultrafast, CABAC | MISMATCH NAL 6 byte 89 |
| exp007/008 | x264 / oracle | forza, fast, CAVLC | MISMATCH NAL 0 byte 1 |

NAL 6 is the P-slice of frame 4. Frames 0-3 now match byte-for-byte in every
ultrafast experiment (previously only frames 0-1 matched). The authoritative
2-frame sweeps remain green (CAVLC 1360/1360, CABAC 1360/1360, I-frames 72/72).

## CONFIRMED root cause #1 — temporal MV predictors (FIXED)

`x264_mb_predict_mv_ref16x16()` (`common/mvpred.c:580-603`) appends three
**temporal** predictors from the reference frame's `mv16x16` cache:
collocated, right and bottom MBs, scaled by `(curpoc-refpoc)*inv_ref_poc`
(= 256 for consecutive P frames) and rounded to fullpel with `(mv+2)>>2`.
The oracle only generated the four spatial mvr predictors, so chained
P-slices picked wrong MVs from frame 2 onward.

Evidence: for frame 2 MB 9, x264's mvc list was
`[8,60][24,-56][0,8][8,-52][-24,64][-56,32][4,-52]` — the last three are
temporal. Dumping x264's `l0->mv16x16` and the oracle's reference MV cache
showed identical temporal values once threaded through.

Fix: `vk_encode_p_frame_recon_mv()` / `vk_cabac_encode_p_recon_frame()` now
take `ref_mv`/`cur_mv` arrays (the `mv16x16` cache), append the three
rounded temporal candidates, and export the current frame's analysis MVs.
This moved the first divergence from NAL 4 (frame 2) to NAL 6 (frame 4).

## Hypotheses (ranked)

### H1 — mv16x16 cache contents for skipped / intra MBs (NEXT)
At frame 4 MB 0 x264's temporal list is
`[0,0]×4 [-20,-44][32,24][-12,80]`; the oracle's is
`[0,0]×4 [-20,-44][32,24][0,0]`. The "below" predictor differs: x264's
frame-3 `mv16x16[16] = [-12,80]` while the oracle's `cur_mv[16] = [0,0]`.
MB 16 is reached through the fast-P_SKIP path (no ME) in the oracle, but
x264 evidently retains an analysis MV there. Need to determine exactly which
x264 path writes `mv16x16` for fast-skip/intra MBs and mirror the cache
persistence across frames (frame objects are recycled; the array is not
wholesale zeroed).

### H2 — ME candidate / predictor cache diverges for intra neighbours
x264 zeroes `mb.cache.mv` for intra MBs but keeps `mb.mvr` for ME candidates.
The oracle mirrors this, but the exact set/order of candidates (left, top,
top-left, top-right, zero, MVP) and the DIA tie-breaking (`dirbits`) may differ
when several neighbours are intra. MB 9 has an intra top neighbour (MB 5) and
an intra top-right (MB 6), which never occurs in the verified 2-frame cases.
Test: log `vk_me16_dia` candidate list and per-candidate costs for MB 9 vs
x264's `analysis.l0.me16x16`.

### H3 — mv_limit_fpel border guard differs
`vk_me16_dia` computes `lim_*` with a 6-pel guard and clips to ±256 qpel.
x264's `mv_limit_fpel` may use a different guard/rounding when the codec
frame's `i_mv_range` is derived from a P-frame reference rather than an IDR.
Test: dump lim values per MB for both encoders.

### H4 — deblocking is active on x264's chained reference
Ultrafast sets `b_deblocking_filter=0`, and slice NAL 3 matches byte-for-byte,
so `disable_deblocking_filter_idc=1` in both. We verified the *unpadded*
reconstructed frame 1 is bit-identical (`--dump-yuv` frame 1 vs oracle recon),
so this is considered unlikely, but the padded border was not compared.

### H5 — preset differences (non-ultrafast presets)
NAL 0 (SPS) differs at byte 1 for every preset above ultrafast: x264 emits
`profile_idc=0x64` (High) with 8x8dct/deblocking, while the oracle emits
`0x42` (Baseline). This is a *parameter-coverage* gap, not an entropy bug.
The oracle needs the missing SPS/PPS/param fields plus the corresponding
analysis features before these presets can match.

### H6 — non-determinism in chained P-slices (FIXED, PR #188)
Running the oracle twice on the same forza crop produced different streams
(SHA prefixes `B08230014A75`, `6E65C090EB8F`, `246F97E70F4D`). Root cause:
the oracle used `LPAD=16`/`CPAD=8` reference-plane borders while x264 uses
`PADH=PADV=32` (`common/frame.h:32-34`). High-motion MVs (e.g. -132,-232 qpel
at frame 4 MB 14) read past the narrower border into uninitialised heap.
Fix: `LPAD=32`/`CPAD=16` in `pframe.c` and `cabac_enc.c`, with matching CLI
stride/offset changes. Verified: 3 consecutive encodes now produce the same
SHA (`6DC3A6760B39...`), and 2-frame sweeps stay 1360/1360.

### H7 — one extra bit in MB 13 of frame 4 (NEXT, precisely isolated)
A corrected per-MB write tracer (resetting the MB tag before the oracle's
in-function slice header, and skipping the 18 header bits when aligning with
x264's post-header trace) shows frame 4 MBs 0-12 and 14-15 are bit-identical.
Only **MB 13** differs:
```
x264:   100011011100000100001001110011101110010111101   (45 bits)
oracle: 10001101110000010000100111001110111001011101    (44 bits)
```
Common prefix 42 bits; x264 has one extra `1` near the end. MB 13 is the
I16-in-P MB with `cbp_chroma=1` (chroma DC only, no luma AC). Its VLC-level
dump showed matching coeff_token/level/total_zeros/run_before codes for the
luma DC block, so the extra bit is likely in the chroma DC block's
`total_zeros`/`run_before` tail or a duplicated `mb_qp_delta` se(0).
Earlier "MB 15" conclusion was an artefact of a stale MB tag in the tracer.

Additional evidence (bit-position instrumentation of the correct writer
functions, frame 4 / MB 13):
```
x264    luma DC 585->614, chroma DC0 614->617, chroma DC1 617->619
oracle  luma DC 585->614, chroma DC0 614->617, chroma DC1 617->619
```
All three residual sections have IDENTICAL start/end bit positions, so the
extra bit is not in those sections' lengths. x264's `x264_total_zeros_2x2_dc`
and the oracle's `vk_total_zeros_2x2_dc` tables are byte-identical. The
whole-slice W-trace totals only 704 bits while the NAL payload has 952 bits,
so the tracer demonstrably misses writes; the exact MB attribution of the
8-bit-longer region is therefore still uncertain and needs a complete
write-trace (including all `bs_write*` macro paths) before a fix is safe.

NAL-byte-level decoder (`build/cmp_symbols6.py`, using `decode_full_pslice.py`)
gives a more reliable result: for NAL 6 both streams decode IDENTICAL slice
headers and IDENTICAL MB syntax through all 16 macroblocks:
```
hdr end bit 26; MB0 P mt0 mvd(-44,36); MB1 SKIP 16; MB2 P mt1 mvd(0,-5);
MB3 P mt2 mvd(3,0); MB4 SKIP 4; MB5 P mt1 mvd(0,1); MB6 P mt0 mvd(-1,1);
MB7 SKIP 1; MB8 P mt1 mvd(0,0); MB9 P mt0 mvd(4,6); MB10 I16 cbp3;
MB11 P mt0 mvd(0,0); MB12 SKIP 6; MB13 SKIP 6; MB14 SKIP 32;
MB15 P mt0 mvd(-2,0)  -- bit 174 in both
```
So the 8-bit divergence begins AFTER the last MB header, in residual data.
The decoder cannot parse the residual blocks (`no coeff token`), which is
itself evidence that the residual VLC state diverges there.

**Per-block residual dumps from both encoders (frame 4) contradict that:**
`build/_blk4.py` logged every `cavlc_block_residual_internal` /
`vk_cavlc_block_residual` call and `build/cmp_blk4.py` compared them:
```
counts 40 / 40
ALL BLOCKS MATCH (levels truncated to total)
```
Every block's `mb`, `cat`, `nC`, `total`, `trailing`, `mask` and all nonzero
level values are identical. Combined with the identical MB headers, this
means the 8-bit divergence is NOT in any logged residual block or header.
It must be in a write that bypasses those hooks — most likely the
`x264_coeff0_token` for all-zero blocks (written directly by x264's macro,
so not logged) or the end-of-slice skip_run.

**coeff0 tokens also match.** `build/_coeff0_x.py` + `build/_coeff0_4.py`
logged every zero-block token from both encoders (x264 logs each twice due
to its analysis/write macro calls; the oracle once). Unique values:
```
mb=13 nC=4 sz=2 bits=1   (both)
mb=14 nC=0 sz=1 bits=1   (both)
mb=15 nC=0 sz=1 bits=1   (both)
all other zero blocks nC=0 sz=1 bits=1 (both)
```
So headers, 40 residual blocks, coeff0 tokens and skip runs all match, yet
NAL 6 differs by exactly 8 bits (59 vs 51) and then resynchronises. This
points to a VLC *encoding* difference for an identical symbol (e.g. a
level-suffix state or table index) in a path not covered by the per-block
dumps. The bit-position instrumentation needed to isolate it could not be
completed (the oracle build rejected the `vk_bs_pos` call), so no fix was
committed.

**Level VLCs also match.** `build/_lvl4.py` logged the level-suffix state and
emitted `(size,bits)` for every coefficient in frame 4 (x264 logs each twice
due to analysis+write; oracle once):
```
x264 60 writes -> dedup 30; oracle 30 writes
ALL MATCH  (suffix, level value, VLC size and bits identical)
```
`build/cmp_tables.py` also verified all static VLC tables are identical:
```
total_zeros      entries 135 / 135, diff 0
total_zeros_2x2  entries 9 / 9,   diff 0
coeff0           entries 6 / 6,   diff 0
run_before_init  entries 42 / 42, diff 0
```
Thus every logged element (headers, 40 blocks, coeff0, level VLCs, skip
runs) and every static table match, yet NAL 6 differs by 8 bits. The only
remaining unlogged writes are the trailing-sign bits (`bs_write(trailing,
sign)`), level escape codes (`block_residual_escape`), and the per-mask
generated `run_before` table. The next diagnostic must hook those three.

**All three were then logged and all match.** `build/_rest4.py` instrumented
trailing signs, total_zeros and run_before for frame 4:
```
TS  x264 40 / oracle 40   -> identical sequences
RB  x264 40 / oracle 40   -> identical sequences
TZ  x264 logs 2x per block (analysis+write); values match oracle 1x per block
    e.g. mb=13: {sz3/bits5, sz1/bits1} in both
```
Every logged CAVLC element and every VLC table is now proven identical for
frame 4, while NAL 6 still differs by exactly 8 bits (59 vs 51) and then
resynchronises. The remaining candidates are write-order/state effects not
captured by per-element logs (e.g. how `i_suffix_length` carries across
blocks in a path not exercised by the 2-frame sweeps, or an emulation-
prevention/byte-alignment edge case). No safe fix was established; no source
change was committed.

Bit-level alignment of the divergent region (NAL payload bits):
```
common prefix 808 bits, common suffix 85 bits
x264 middle (59 bits): 0000010000 + [47-bit common run] + 11
oracle middle (51 bits):           [47-bit common run] + 0100
```
x264 has 10 extra bits before the shared 47-bit run and 2 fewer after it.
`0000010000` resembles a long VLC/escape prefix, yet no logged level,
total_zeros, run_before, sign or coeff0 write differs. This is the exact
signature that needs a byte-level (emitted-NAL) write trace to resolve.

## What is proven

- IDR CAVLC and CABAC paths: byte-exact, including 8-frame clips on warzone.
- Frame-1 P-slices: byte-exact on all clips.
- CABAC flush terminator depends on `h->i_frame & 31`
  (`0x35a4e4f5 >> frame & 1`); fixed by threading the frame index through
  `vk_cabac_encode_*_recon_frame`. This made 8-frame CABAC exact on warzone.
- Frame-2 divergence is content-dependent (flat and warzone crops pass;
  high-motion forza/fortnite fail), consistent with H1/H2/H3.
